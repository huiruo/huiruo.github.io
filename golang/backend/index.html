01.缓存穿透、击穿和雪崩有什么区别？

参考答案：

  • 穿透：请求不存在的数据，缓存和数据库都未命中；可用参数校验、空值缓存、布隆过滤器。
  • 击穿：缓存服务仍可用，但一个热点 Key失效，大量请求同时回源同一份数据；可用单飞、互斥重建、逻辑过期。
  • 雪崩：很多不同 Key在同一时段失效，或缓存集群整体不可用，广泛的请求同时回源；可打散过期时间、限流降级和提供多层容错。

三者的核心区别是：穿透针对“查不到的数据”，击穿针对“单个热点 Key”，雪崩针对“大量 Key 或整个缓存服务”。

不一样，区别在失效范围：

  • 缓存击穿：缓存服务正常，一个热点 Key过期，很多请求同时查询同一条数据。
  • 缓存雪崩：很多不同 Key同时过期，或整个缓存集群不可用，广泛请求同时回源。
问题典型场景流量表现主要影响解决方案
缓存穿透攻击者不断请求不存在的商品 ID；客户端因参数错误持续查询已删除用户每次请求都绕过缓存访问数据库，流量可能持续存在数据库承受大量无效查询，连接池和 CPU 被消耗，正常请求变慢参数校验和限流；缓存空值（短 TTL）；布隆过滤器拦截不存在的 ID
缓存击穿一个秒杀商品或热搜榜单的热点 Key 刚好过期，缓存服务本身正常数万请求集中回源查询同一个数据单表、单行或下游接口形成热点，可能引发锁竞争、超时和级联重试singleflight 或分布式互斥锁使一个请求重建；逻辑过期并异步刷新；热点预热
缓存雪崩批量导入的很多 Key设置了相同过期时间；或缓存集群故障、网络中断大量不同 Key同时未命中，回源流量覆盖较大业务范围数据库和下游服务整体过载，可能导致接口大面积超时甚至服务不可用TTL 加随机抖动、分批预热；缓存集群高可用和多级缓存；限流、熔断、降级保护数据库

面试可补一句：

  • 缓存穿透是反复请求不存在的 key，应用可对空结果短暂缓存、做参数校验或使用布隆过滤器；
  • 缓存击穿是热点 key 失效时并发回源，可用互斥更新、逻辑过期或提前刷新；
  • 缓存雪崩是大量 key 同时过期，可通过 TTL 加随机抖动、分批预热和降级处理。它们主要是服务端缓存问题，但 CDN / HTTP 缓存策略设计会直接影响回源压力。

例如商品详情缓存的正常流量为每秒 1 万次：请求随机的不存在商品属于穿透；某个爆款商品缓存过期后，其每秒 5 千次请求同时回源属于击穿；大量商品缓存同时过期，使接近每秒 1 万次请求全部回源则属于雪崩。

应对方案也有代价：空值缓存要设置较短过期时间，避免真实数据创建后仍返回空；布隆过滤器可能误判且需要维护；单飞或互斥锁必须设置超时并处理重建失败；随机过期时间只能降低同时失效概率，不能解决缓存集群整体故障。因此还应设置数据库保护、限流、熔断和降级策略，避免缓存故障演变成更大的流量尖峰。

常见追问： 热点 Key 永不过期是否能解决击穿？只能降低因自然过期造成的击穿，还要处理数据更新、节点淘汰和缓存服务故障；通常应配合逻辑过期、异步刷新及回源保护。

44. 如何处理热点 Key？

参考答案： 先通过访问频率、带宽和分片指标确认热点。可使用本地缓存、请求合并、只读副本、Key 分片或预计算降低单点压力。分片会增加聚合与一致性复杂度，本地缓存则带来更多副本和过期问题。

45. 消息为什么通常需要按“至少一次”设计消费？

参考答案： 消费者可能在业务提交后、确认消息前崩溃，消息因此再次投递。消费者应通过业务唯一键、去重表、状态机或天然幂等写入处理重复。仅在内存中记录已处理消息无法跨重启可靠去重。

Redis 和 MySQL 的区别与使用场景

Redis 是以内存访问为主的键值数据库，适合低延迟访问和临时状态管理；MySQL 是关系型数据库，适合需要长期保存、事务保障和复杂查询的业务数据。两者通常配合使用。

对比项RedisMySQL
数据模型Key-Value，支持字符串、哈希、列表、集合、有序集合等结构表、行、列，通过主键、外键及 SQL 组织和查询关系数据
存储与持久化主要在内存中访问数据，可通过 RDB、AOF 持久化；故障时的数据丢失窗口取决于配置主要在磁盘上持久化，并通过缓冲池加速访问；通常作为业务数据的权威来源
查询能力按 Key 和数据结构执行操作，不适合复杂关联查询支持条件过滤、关联、聚合、排序和索引查询
事务能力支持原子命令、Lua 脚本及 MULTI/EXEC，但事务不支持 MySQL 式回滚InnoDB 支持 ACID 事务、隔离级别和回滚，适合多条业务数据的一致性更新
性能与成本内存访问延迟低，适合高频简单操作；内存成本较高，需控制容量和淘汰策略性能受索引、SQL、锁和磁盘访问影响；适合保存较大规模的结构化数据
过期机制原生支持 Key 的 TTL，适合有有效期的数据通常通过过期时间字段和定时清理实现

Redis 的典型使用场景：

  • 热点缓存：缓存商品详情、用户资料等高频读取数据，降低 MySQL 查询压力。
  • 临时状态：保存验证码、会话、短期令牌，并设置 TTL。
  • 计数与排行：通过原子自增实现计数，通过有序集合维护排行榜。
  • 限流：结合计数、TTL 或 Lua 脚本实现固定窗口、滑动窗口等限流策略。

MySQL 的典型使用场景：

  • 核心业务存储：保存用户、订单、支付记录、库存等需要可靠持久化的数据。
  • 事务操作：在一个事务内完成订单创建、库存扣减等多条数据库更新。
  • 关系与统计查询：关联用户、订单、商品，按条件筛选、汇总业务数据。

配合使用的例子： 商品详情以 MySQL 为准，读取时先查 Redis，未命中再查 MySQL 并回填缓存；更新时先提交 MySQL，再删除对应缓存，并对删除失败进行重试。这个模式仍有并发读写导致短暂不一致的可能，需要结合业务要求设计一致性策略。支付金额、库存扣减等关键判断应通过数据库事务、条件更新等机制保证正确性，不能仅依赖缓存值。

Redis 使用时需要注意什么？

使用 Redis 时，要重点考虑过期策略、内存容量、阻塞操作、数据一致性和故障处理，不能只关注读写速度。

注意事项可能出现的问题建议做法
Key 命名与过期时间命名冲突、无用数据长期占用内存、大量 Key 同时过期按业务统一命名，例如 product:detail:123；为临时数据设置 TTL，并加入随机抖动；尽量用带过期参数的 SET 原子写入
内存与淘汰策略内存耗尽后触发淘汰或写入失败设置 maxmemory，根据用途选择淘汰策略；缓存可考虑 allkeys-lru 或 allkeys-lfu；会话、锁等不可随意淘汰的数据应与普通缓存隔离，并做好容量规划
大 Key 与热点 Key大 Key 增加传输和删除成本；热点 Key 使单个节点过载控制单个值大小及集合元素数量；大集合分批读取，删除大 Key 可考虑 UNLINK；热点数据可用本地缓存、请求合并等方式减压
慢命令与长脚本命令执行占用主线程，拖慢其他请求生产环境避免 KEYS *、无界的全量读取和长时间 Lua 脚本；遍历用 SCAN 分批执行，注意它可能返回重复元素，且不是一致性快照
缓存与数据库一致性数据库已更新，缓存仍返回旧值常见做法是先提交数据库，再删除缓存，并为删除失败提供重试；设置合理 TTL；强一致业务不能只依赖缓存判断
缓存失效与故障穿透、击穿、雪崩导致数据库瞬间过载配合空值缓存、请求合并、TTL 抖动、限流和降级；故障时限制回源并发，避免所有请求直接压向数据库
持久化与主从复制重启或故障切换后丢失部分已确认写入根据可接受的丢失窗口配置 RDB、AOF；主从复制通常是异步的，高可用不等于零数据丢失；重要数据要有可靠存储和恢复方案
原子性与分布式锁多条命令交错执行、锁提前过期、误删别人的锁单条命令通常具有原子性，多步操作可用 Lua；加锁用 SET key token NX PX，解锁时原子校验 token 再删除；设置合理租期，关键写入仍需业务侧并发保护
连接与重试连接泄漏、请求无限等待、超时重试导致重复操作复用客户端连接池，设置连接和读写超时；限制重试次数；超时不代表命令未执行，扣减、入队等操作需考虑幂等
安全与监控未授权访问、数据泄露、性能恶化未及时发现使用私有网络、ACL 和最小权限，按需启用 TLS；监控内存、命中率、淘汰数、延迟、慢日志及复制延迟

Go 项目中： 通常复用一个并发安全的 Redis 客户端，通过 context 控制请求截止时间；区分 Key 不存在与连接失败，避免把 Redis 故障当作普通缓存未命中而无限回源。
